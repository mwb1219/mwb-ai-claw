# DDD 领域建模

## When to Use

用户要求进行领域建模、划分限界上下文、设计聚合/实体/值对象，或按 DDD 思路组织代码。

## 工作流

1. **战略设计**：识别业务能力 → 划分限界上下文（每上下文单一职责、明确依赖方向）→ 定义上下文间关系（防腐层 / 共享内核 / 开放主机服务）
2. **战术设计**：在每个上下文内识别——
   - **实体（Entity）**：有唯一标识、有生命周期、可变；如 Order、Session
   - **值对象（VO）**：无标识、不可变、由属性整体定义；如 Address、Money
   - **聚合（Aggregate）**：一组内聚对象，聚合根是外部唯一访问入口；事务边界 = 聚合边界
   - **领域服务（Domain Service）**：跨实体/聚合的领域逻辑，无状态
   - **仓储（Repository）**：聚合持久化的唯一通道，接口在 domain、实现在 infrastructure
3. **输出**：上下文图（mermaid） + 每个聚合的实体/VO/方法清单 + 仓储接口

## 设计原则（贴合 COLA/DDD 架构）

- 依赖方向：domain 不依赖 infrastructure / interfaces，依赖倒置
- 应用服务（application）编排用例、调用领域服务，不在其中放业务规则
- 避免贫血模型：能放进实体的业务规则不要外置到 Service
- 每个聚合尽量小，跨聚合一致性用最终一致性（事件）而非事务

## 要点

- 建模前先确认业务规则来源（用户描述/现有代码/文档），不确定时列出开放问题
- 输出物对齐项目分层：domain/xxx（实体）+ application（应用服务）+ infrastructure（仓储实现）
